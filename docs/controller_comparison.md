## 2. 实现

入口增加 `--controller ideal|nmpc`，默认选择 `nmpc`。两种模式共用 A*、RISP、MINCO、CmdTraj、状态机和传感器。

Ideal 依据 SUPER `perfect_drone_sim` 直接赋值位置和速度。加速度与偏航通过原平坦性关系生成姿态。规划器读取参考加速度和加加速度。机体尺寸及原几何碰撞检测保持不变。

NMPC 执行链为：SUPER CmdTraj → 10D TurboMPC → 角速度控制器 → 旋翼分配与电机 → Newton。

| 项目 | 配置 |
|---|---|
| 预测状态 | 位置 3 维、四元数 `[w,x,y,z]` 4 维、世界系速度 3 维 |
| 对外控制输入 | 总推力加速度 m/s²、机体系角速度 rad/s |
| 求解器内部输入 | 总推力 N、机体系角速度 rad/s |
| 单位换算 | 求解器推力除以质量 0.752 kg；内环恢复为 N |
| 预测时域 | 16 步 × 0.02 s = 0.32 s |
| 滚动求解 | 50 Hz 仿真时钟；执行首个输入并移动优化序列 |
| 控制步进 / 物理内环 | 100 Hz / 400 Hz |
| SQP / ADMM 最大迭代 | 3 / 500 |
| ADMM 容差 | 绝对 1e-5，相对 1e-4 |
| 角速度反馈增益 | `[8, 8, 8] s⁻¹` |
| 推力与角速度约束 | 总推力 0–34 N；角速度上限 `[10, 10, 4] rad/s` |
| 旋翼物理限制 | 每旋翼 0–8.5 N，由原 RotorActuator 执行 |
| 电机一阶响应 | 0.033 s，仅保留在实际执行系统 |

成本跟踪未来位置、速度、姿态及参考输入。四元数参考与当前姿态保持同号。成本权重和配置均写入 JSON 汇总。未来参考从最后正式发布的 CmdTraj 采样，保持原轨迹时间戳和备用切换。

10D 模型、ADMM、QP、Triton 核与 nvmath/cuDSS 组件已复制到当前仓库。来源为 Isaac-L2F `e36743e8076bfe12b3e11911e2f1f866d61ae158`。SQP 保留源线性化、线搜索与滚动初值方法。未引入学习模块。文件来源与哈希见 [sources.json](sources.json)。

旧 GeometricTracker 和仅调用该控制器的回放/对比脚本已删除。17D 预测模型已由 10D 模型替换。

## 4. 失败归因

### 规划端

两次 Ideal 的实际机体和参考机体均无几何碰撞，且均到达终点。Dense 的中途低速总时长为 2.31 s。它仍有大量超时和优化失败。

| 规划状态 | Ideal Medium | Ideal Dense | NMPC Medium | NMPC Dense |
|---|---:|---:|---:|---:|
| REPLAN_OVERTIME | 26 | 126 | 43 | 26 |
| EXP_SIM_OVERTIME | 3 | 44 | 0 | 0 |
| EXP_OPT_FAILED | 1 | 32 | 0 | 0 |
| PATH_SEARCH_FAILED | 0 | 1 | 0 | 0 |
| BACKUP_OPT_FAILED | 0 | 0 | 9 | 2 |
| BACKUP_CORRIDOR_FAILED | 0 | 0 | 0 | 5 |
| ON_BACKUP_WAIT_FOR_REST | 0 | 18 | 6 | 7 |

当前规划端的主要已观测问题是耗时、优化失败和备用等待。失败次数不能全部归为 A* 或 RISP 的几何路径失败。

### Medium 的控制失败

首次实际几何碰撞发生在 6.1075 s，首次接触记录为 6.11 s。参考机体全程无几何碰撞，也未越界。

碰撞前最大位置偏差为 1.430414 m。首次碰撞时偏差为 1.067636 m。当时仍执行主轨迹。其最后发布的 plan46 为成功规划，最近返回的 plan52 因原超时规则被拒绝。跟踪偏离先于碰撞。

### Dense 的控制失败

实际机体在 5.65 s 首次越界。6.14 s 时，实际高度为 -1.014661 m，同步参考高度为 0.629920 m。参考高度全程为 0.477954–0.745487 m。

实际机体与参考机体都没有几何碰撞记录，接触力也为 0。参考全程未越界。此次终止来自姿态和高度跟踪失效。

### 预测与执行的差异

未发现状态索引、四元数顺序、推力单位或参考时间接入错误。总推力单位转换误差小于 4.1e-6 N。活动阶段的参考发布时间距记录状态为 10–20 ms。

首个 20 ms 动作中，10D 模型预计 Medium 和 Dense 分别转动 11.12°、9.24°。实际仅转动 0.269°、0.243°。源模型立即使用期望角速度，真实角速度由有限增益的内环和电机响应产生。

Medium 的首次动作同时要求近零总推力和较大角速度。旋翼限幅后，请求的滚转力矩从 -0.0526 N·m 变为 +0.0507 N·m，总推力变为 1.0325 N。4.79 s 时，期望俯仰角速度已反向至 -2.11 rad/s，实际仍为 +7.54 rad/s。

这些记录支持两个主要原因：角速度响应与预测不一致，以及旋翼限幅改变推力和力矩。总推力与角速度的独立边界不能保证二者可同时实现。当前成本权重和迭代预算也可能影响动作激进程度。已保存数据没有逐次预测轨迹或 QP 残差，不能进一步分离这些因素。

因此，当前 10D 配置可以稳定悬停，但尚不能可靠跟踪这两个场景的高速轨迹。后续应先处理角速度响应和分配可行性。

## 5. 求解耗时与实验条件

环境使用 NVIDIA GeForce RTX 4090、Python 3.12.14、PyTorch 2.11.0+cu130、Newton 1.6.1、Numba 0.68.1。`OPENBLAS_NUM_THREADS=1`、`OMP_NUM_THREADS=1`。飞行依次运行。

表 1 的求解 P50/P95 包含起飞等待阶段的所有真实求解。构造函数预热单独记录，不计入这些百分位。每次求解在 CUDA 同步前后计时。

|---|---:|---:|---:|---:|
| Medium seed2 | 351 | 174，49.57% | 36.224 / 74.294 | 121 / 121 |
| Dense seed4 | 307 | 109，35.50% | 36.130 / 67.134 | 50 / 50 |

两次记录的最大单次求解约为 3.69 s，均发生在仿真时刻 0。它们保留在统计中。50 Hz 表示仿真时钟上的控制频率，当前墙钟耗时无法支持该频率的实时飞行。

两种模式沿用同一规划进程和墙钟定时规则。执行开销、实际状态及传感器观测不同，因此重规划序列也会不同。归因使用各次飞行自己的参考轨迹，并检查故障之前的误差。

复现实验时使用新目录，避免覆盖数据：

```bash
controller_run="results/controller_comparison_$(date +%Y%m%d_%H%M%S)"
for controller in ideal nmpc; do
  OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 .venv/bin/python -m isaac_pathcover.demo \
    --controller "$controller" --scene medium --seeds 2 --duration 90 \
    --output "$controller_run/$controller/medium"
  OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 .venv/bin/python -m isaac_pathcover.demo \
    --controller "$controller" --scene dense --seeds 4 --duration 90 \
    --output "$controller_run/$controller/dense"
done
```

每次运行保存 `source_hashes.json`。Ideal Medium 的快照仅有 `trajectory/lbfgs.py` 与最终版本不同，差异是缓存修复。其执行代码与规划数值公式不变。其他 3 次飞行的源码哈希与最终版本完全一致。
